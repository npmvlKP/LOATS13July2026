### 🟠 F8-H-02 — Rule 7 modification counter is process-global, in-memory, and resets on restart; per-order semantics absent and no gate at the modify boundary

- **Issue ID:** F8-H-02
- **Category:** CMP Conformance (Rule 7) / Reliability
- **Severity:** High
- **Confidence Level:** Certain
- **Evidence:** `rules.py:52` `self.modification_counter = 0` (single int on the singleton engine); `increment_modification_counter` / `reset_modification_counter` / `get_modification_count` at `:472-483`; the trailing driver calls `increment_modification_counter()` per SL-M modify under a **per-cycle** cap (`orchestrator.py` update loop: `modifications_this_cycle >= cfg.max_modifications` → stop). `openalgo.py::modify_order` (sync `:489`, async `:928`) contains **no** modification-limit gate — grep: `check_modification_limit` exists nowhere at HEAD (removed with the legacy path). No SQLite `modification_counts` table exists (grep: zero hits). HC-23 only reads settings values, so it stays green.
- **Root Cause:** TODO-17's spec was "25, wired + persisted + fail-closed per-order"; the implementation delivered "25, wired, per-cycle-capped" — persistence and per-order dimensions silently dropped while the check that verifies them verifies only the settings number.

A process-lifetime counter (a) resets on restart, resetting every order's budget; (b) is not keyed by `order_id`, so one busy order can consume another's budget within a cycle; (c) is enforced only in the trailing driver — any other `modify_order` caller bypasses it entirely.
- **Impact:** Long-running ratcheting can exceed 25 modifications per order across cycles/restarts; the CMP ceiling is not enforced at the API boundary.
- **Possible Consequences:** Broker rejection of the 26th modification; audit-trail non-conformance; ratchet stalls in production that tests cannot reproduce.
- **Risk Assessment:** High (compliance + operational).

- **Recommended Tests:** (1) Counter-survives-restart test: modify order N times, reconstruct engine/DB, counter continues from persisted value; (2) per-order isolation: two orders, 25 modifications each, both accepted, 26th on either rejected; (3) fail-closed test: DB error during counter read → modification rejected with explicit reason; (4) boundary test at `modify_order` itself (not just the driver): 26th direct modify call raises/refuses; (5) HC-23 extension asserting the table exists and the gate is wired at the modify boundary.
